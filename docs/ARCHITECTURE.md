# Architecture and source map

This describes the v1.1.2 source line. The toolkit is a Node.js authoring/build project whose output is a standalone browser document. Ordinary quiz building and playback do not require the optional Python DOCX toolchain.

## Data flow

```text
Authoring brief and approved sources/assets
  -> reviewed configuration JSON
  -> compiler validation + bundled runtime/media
  -> self-contained offline HTML
  -> browser engine, presentation and host controls
  -> local session state, resume copy and optional reports
```

Question-source research happens before compilation. The build scripts do not fetch cited sources to establish factual truth. Network access for an assistant's research is separate from the compiled quiz's offline gameplay.

## Session identity and recovery

Event identity and a configuration fingerprint separate saved sessions. Changes to questions or rules can create a different profile, so an old checkpoint is not automatically a valid continuation. Recovery checks protect the score ledger and recorded opportunities rather than trusting arbitrary imported state.

A **Save resume copy** download includes the quiz and checkpoint; reopening it resumes paused. Browser-local storage is a convenience that may be unavailable. Keep the exact original file for an ongoing event and rehearse recovery on its actual browser.

The optional audience window receives only selected public display fragments. It is not a second scoring engine or a secure answer vault. Screen mirroring can still expose the host's screen. The full host HTML necessarily contains questions and answer keys.

## Reproducibility and release boundaries

[build-provenance.cjs](../scripts/build-provenance.cjs) computes `runtime-source-v1` from runtime, build, dependency and license inputs. Git state, the root README, Markdown under `docs/` and generated outputs are outside that runtime identity. Every file under `src/` is an input regardless of extension, along with the explicitly listed build, dependency and license files. An edit limited to the root README or Markdown under `docs/` does not require a new quiz profile or regenerated runtime bundle; a change to any included input does require the matching rebuild and provenance checks.

The release package has a separate exact source commit/tree identity. [build-release.cjs](../scripts/build-release.cjs) checks committed artifacts, aligned versions, provenance, DOCX binding and mirror correspondence before packaging. [release.json](../release.json) selects the version and release notes; [the workflow](../.github/workflows/release.yml) limits publication to the trusted main branch.

The [GitHub setup guide](GITHUB_SETUP.md) remains the release procedure. Do not bump versions, republish old tags or deploy Pages merely to update documentation.

## Validation layers

1. Configuration validation checks supported structure, rules and input boundaries.
2. Automated tests exercise engine/compiler, recovery, presentation adapters, provenance and packaging.
3. Browser checks cover actual interaction and rendering in the environments tested.
4. Independent content review evaluates each question and source.
5. Live rehearsal verifies the host's chosen browser, sound, display and recovery.

These layers answer different questions. [Release QA](RELEASE_QA.md) states dated results and untested environments; passing one layer cannot stand in for the others. For changes, start with [Contributing](../CONTRIBUTING.md) and preserve the [security boundaries](../SECURITY.md).
