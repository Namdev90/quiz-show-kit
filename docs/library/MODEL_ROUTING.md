# Choose capabilities, then tools

Use tools and models that materially improve the task. Do not invoke every connector, require a paid plan, or hard-code a provider's “best model” into this reusable prompt. Available names, pricing, limits and access change. Inspect what this session actually offers; verify current official documentation before recommending a named product or model.

**Default order:** repository asset/preset → approved upload → available specialist tool/plugin → established open-source library → small custom adapter. Reuse the engine, its compiler and vendored libraries. Tool discovery should be a filtered metadata lookup for the current need, not a dump or trial of every connector. Read the relevant skill once when it materially helps. A new website builder is not part of this workflow.

| Work | Needed capability | Route |
| --- | --- | --- |
| Brief and preset choices | Reliable instruction following and short conversation | The current assistant is usually enough |
| Research and source checks | Web retrieval or readable authoritative documents | Search/browse with source attribution; use a relevant subject database where it adds value |
| Difficult question reasoning | Strong subject reasoning and evidence comparison | Use a more capable reasoning model only for the hard/uncertain items if available |
| Data graphs and exact diagrams | Accurate reusable asset, deterministic plotting or diagram tool | Reuse accurate diagrams first; do not use image generation to fabricate data or required labels |
| Decorative theme imagery | Repository media or an image tool with file export | Reuse first; use the [media shelf](MEDIA_TOOLING.md) for missing assets |
| Clear synthetic narration | Suitable recording, verified local speech or synthesis with file output | Reuse matching clips; generate only missing/changed scripts before building |
| Personal voice | Actual teacher recording or an explicitly consented supported voice tool | Incorporate real uploads; never claim an assistant has recorded a human voice |
| Settings and complete event files | Read/write files, repository access and build execution | Use the real compiler, validated configuration and approved assets |
| Engine extensions or fixes | Source editing and focused automated tests | Use a coding environment; review diffs, verify the current showcase and preserve its historical archive |
| Visual QA | Real browser rendering and interaction | Inspect the relevant screen/flow; distinguish DOM simulation from a real browser |
| Public contribution | GitHub read/write tools, actual patch and authorization | Open a real PR only when those requirements are met |

Use the lightest capable route for routine formatting, citations and preset application. Escalate only where uncertainty, complexity or a failing check warrants it. Independent research/review tasks can run in parallel; keep dependent edits and source-of-truth changes coordinated.

Keep both input and output small: load the needed module/sections, reuse verified choices and sources, summarize findings once, return patches instead of whole-file rewrites, and show only useful command output. Request only the tool fields/results needed. Reuse unchanged approved narration and media; batching and parallel work should eliminate duplicated context, not multiply it. Never compress away exact questions, source evidence, permissions, configuration constraints or failing diagnostics. A short launch prompt still incurs the cost of instructions retrieved afterward; do not promise a token-saving percentage without measuring it.

These instructions guide this session. They do not change a user's global AI settings, subscription, default model or other chats. Offer a supported model switch only when it helps; if switching is unavailable, work with the current capabilities and state any material limitation.

Do not ask teachers to configure developer tooling or API keys. If this session lacks an essential capability, finish what is possible and provide a compact handoff with the exact files, source revision, selected settings, pending steps and known limitations. Never claim that changing models alone grants browsing, filesystem access, microphone permission or GitHub authorization.

A model's output is not evidence by itself. Verify factual claims against sources, validate its configuration, inspect generated media, and test code changes with the tools actually available. Tool-routing recommendations are part of the workflow, not promises that every platform supports every feature.
